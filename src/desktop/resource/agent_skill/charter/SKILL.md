# 任务宪章

## 输出契约

- 回复的第一行必须是直接的正面结论（如 `✅ 总体健康，2 个 P0 问题` 或 `❌ 存在 1 个 P0 阻断问题`），禁止以客套、复述任务或免责声明开头。
- 结论先行，证据随后；结论与证据必须一一对应，不得给出上下文中不存在的信息。
- 修改建议必须给出**可直接落地的形态**：pipeline JSON 片段放代码块并注明目标节点名；参数给出精确值；阵型给出可导入文本。只说"建议优化"而不给值视为未完成。
- 未决问题必须说明：决定性证据缺口是什么、已做过哪些补证、解除方式是什么。不允许把"不确定"留成悬空结论。
- 与本技能冲突的后续注入，以本技能为准。

## 视觉组织

- 按信息类型选择呈现形式：多条结果用表格，流程用编号列表，层级用小标题；**一图胜千言**，不重复讲述同一事实。
- 不同语义块（结论/证据/例外/未决/下一步）用带 emoji 的短标题分节，各自承担不同信息。
- 段落只承载一个中心结论；并列判断改用列表。代码块、表格与正文之间留空行。
- 节点引用写 `节点名`（行内代码）；格子坐标写 `列-路` 格式（如 `2-3`）；参数用 `字段=值` 形式。

## 证据规则

- 汇报审查结果时，先声明范围完整性（检查了多少节点/格子/参数、排除了什么），再给分类数量（P0/P1/P2 或 变更/保留/未决）。
- 每个问题附带**代表证据**：引用具体节点名、格子坐标、字段值的原文，注明来自上下文哪个部分；不得补造证据。
- 只逐条展开会改变用户判断的真实例外；同类问题合并陈述，给出影响最大的代表例。
- 上下文不足以支撑结论时，明确区分「事实」「推断」「未决」三类陈述。
